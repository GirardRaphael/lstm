The finding

The answer to “why an LSTM?” depends on the dataset

The obvious way to defend an LSTM is to explain that traffic is sequential. The better way is to build the competitor and measure it. XGBoost was trained on exactly the same tensors — same windows, same chronological split, same scaler — just flattened from (n, 24, F) to (n, 24×F). The only thing the tree model loses is the order of the timesteps.

Run on motorway traffic, it wins comfortably. Run on a second, unrelated series, it loses. Both results come from the same code.

MAE is measured in the units of whatever is being predicted, so the two panels must never be compared to each other — only within a panel. That is also why every chart on this page carries one dataset and one dataset only.

The weather and calendar columns behave just as inconsistently: they help the network on bike rentals (41.3 → 38.5) and hurt it on traffic (228.8 → 241.1), while helping the tree model on both. A plausible reading, offered as a hypothesis rather than a result: bike demand leans far more on the same hour yesterday — t-24h carries 21% of the tree’s signal for rentals against 3.6% for traffic — and nobody cycles in the rain, so there is real information in the exogenous columns for a recurrence to use.

The honest takeaway is not “LSTMs are good” or “LSTMs are bad”. It is that the question is empirical, the experiment costs ten seconds, and one dataset is not enough to settle it.

The data

A cycle worth learning, and two flaws worth admitting

Hourly westbound traffic on I-94 between Minneapolis and Saint Paul, October 2012 to September 2018. The target is traffic_volume: vehicles counted during the hour, ranging from 0 to 7,280.

Two imperfections were handled out loud rather than quietly. 7,629 duplicate timestamps — the same hour logged twice with different weather text — are collapsed by averaging the target, which neither invents data nor keeps two conflicting rows. 11,976 hours are missing entirely, mostly a 308-day outage, and they are not interpolated; fabricating traffic volumes would flatter every metric that follows.

Those gaps have a consequence worth stating before anyone else finds it: because windows slide over the rows that exist, 28.7% of the training windows silently span a jump in time. “The last 24 hours” is sometimes 24 readings spread across much longer. Only 5.3% of the test windows are affected, so the headline metrics barely move — and when the offending windows were dropped and the model retrained, accuracy did not improve. The flaw is real; it is not material.

Method

Three decisions carry the whole result

  1. Sort chronologically, collapse duplicate hoursOne row per hour, target averaged where the source disagrees with itself.
  2. Split by time, never by shuffleShuffling would put future hours in the training set. The score would look excellent and mean nothing, because in production only the past exists.
  3. Fit the scaler on the training slice onlyHad it seen the test set, the model would indirectly know the range of the future. That is data leakage.
  4. Give the test set its historyThe first test window needs 24 hours of context, taken from the end of training. That is history, not leakage — the model only ever looks backwards.
  5. Slide the window, reshape to (samples, 24, features)32,436 training sequences, 8,115 test sequences.

All three claims are checked by a test suite rather than asserted in prose, along with the exactness of the gate reconstruction below. python tests/test_pipeline.py — 14 passing.

(24, F) → LSTM 64  return_sequences → Dropout 0.2
        → LSTM 32                   → Dropout 0.2
        → Dense 16  relu            → Dense 1  linear

The last layer has no activation, because the output is a count of vehicles rather than a probability. Overfitting is held back by dropout, a validation split watched every epoch, and early stopping that restores the best weights — it fired at epoch 49 of a permitted 50.

Results

228.8 vehicles an hour, and why that number needed company

On 8,115 hours it had never seen, the model is wrong by about 229 vehicles per hour on average — roughly 11% of the value being predicted. On its own that figure is unfalsifiable, so two naive predictors were scored on identical windows: “the same hour yesterday” (594.3) and “the last hour” (585.6). Had the network not beaten both, the honest conclusion would have been that an LSTM is the wrong tool here.

Inside the network

Not a diagram from a textbook

Keras returns a prediction, not an explanation. So the LSTM cell was re-implemented in NumPy from the trained weights and replayed step by step, recording all four gates of all 64 units at every one of the 24 hours.

The reconstruction is checked against Keras on every run. The maximum absolute difference is 1.17×10−7 — floating-point noise. The replay is the network, so every activation shown here is the one the model computed, not an illustration of one.

Forget gate f = σ(x·Wf + h·Uf + bf)

How much of the existing memory survives this hour. Near 1, the unit holds the whole day; near 0, it starts fresh.

Input gate i = σ(x·Wi + h·Ui + bi)

How much of the new candidate gets written. This hour is worth remembering, or it is not.

Candidate g = tanh(x·Wg + h·Ug + bg)

The content the unit proposes to store, squashed into [−1, 1].

Output gate o = σ(x·Wo + h·Uo + bo)

How much memory leaks out as h = o · tanh(c). A unit can hold information for hours and open only when it matters.

All of it is exported into an Obsidian vault: 114 notes and 27 canvases, including one canvas per hour of the input window so the memory can be watched forming, and one note per neuron carrying its own activation trace. The busiest hour of the test set and the quietest are documented side by side — different subsets of units light up, which is what specialisation looks like from the inside.

Honest limits

What this model cannot do

The headline version sees only past traffic. Snow, a closed lane, a stadium emptying out — all invisible, and all precisely the hours when a forecast would earn its keep. It cannot predict a first-time event, because it extrapolates patterns it has already seen. It is harder to interpret than a decision tree; the vault narrows that gap without closing it. And on this dataset it is both slower and less accurate than gradient boosting.

One claim deserves care, because overstating it is the easiest mistake to make: this model does not control traffic lights. It produces a forecast that a controller could consume.

sensors → hourly history → model → forecast → controller → adaptive lights

The most useful next step is not a bigger network. It is rerunning the multivariate model with a longer early-stopping patience, to separate “the extra features do not help” from “the run stopped after 12 epochs while the baseline got 49”. The current evidence cannot tell those apart.

Running it

Point it at any hourly CSV

The pipeline takes any file with a timestamp column and a numeric column — the bike-rental result above was produced by changing two arguments and nothing else.

python -m traffic_lstm.train --export-vault
python -m traffic_lstm.train --data data/samples/bike_sharing_hourly.csv \
       --target rentals --run-name bike_sharing
python -m traffic_lstm.benchmark --run-name baseline_univariate
python scripts/compare_runs.py
streamlit run app/streamlit_app.py

The Streamlit workbench carries the whole loop: upload a CSV, pick the columns, set the hyper-parameters, watch the loss curve fall live, then step through the network hour by hour and forecast from the final window.
